**Explicit workflow decision (2026-10-03):** implementation (Solidity, `contracts/` Foundry init, etc.) will **not** start after each individual feature's design is finished. Instead, the project will first design all of the initially-planned state functions, then review them together for overall cross-feature consistency, and only then move into implementation. No smart contracts or frontend code have been written yet, and none will be until that consistency review happens.

**Workflow change (2026-10-17, [ADR 0017](decisions/0017-executive-document-anchoring-v1.md)):** the loop is now **initial design → implementation → scenario tests → find issues → redesign**. The initial design still covers **every item in `docs/FEATURES.md`**; after that, the consistency review, then implementation. Hard parts of a function may be deferred to the redesign phase (as for the executive).

## Decided

- Monorepo-style single repository with two main components: `contracts/` (Foundry/Solidity) and `frontend/` (Next.js, deployed on Vercel). No workspace tooling (pnpm workspaces, Turborepo) linking them — kept as independent, self-contained directories.
- Target chains: Ethereum and Polkadot Hub, both EVM-compatible — same Solidity codebase, deploy target switches via config. **Sepolia testnet is the priority network during development.** Mainnet chain choice is explicitly deferred.
- Documentation language: English primary, Japanese alongside for key documents.
- License: MIT.
- Decision history tracked via ADRs in [`docs/decisions/`](decisions/); code-level history via [`CHANGELOG.md`](../CHANGELOG.md).
- Citizenship/residency: a municipality-issued, soulbound, nationality-neutral "resident-link" NFT (proves residency-linkage only, no nationality claim); see [ADR 0003](decisions/0003-resident-link-identity-model.md) for full rationale.
- Taxation (individual, direct payment only): no dedicated contract — a plain stablecoin transfer from the resident's `ResidentLink` address to an officially-attested receiving address; see [ADR 0004](decisions/0004-taxation-payment-rail.md).
- Corporations: an authority-issued, soulbound, on-chain registration NFT per registration/supervision relationship (a corporation may hold several); officer/representative names are public on-chain, their addresses never are; the corporation's own address is a contract governed by a multisig signed with officers' personal keys; see [ADR 0005](decisions/0005-corporate-registration-model.md).
- Credentials (公的証明), general pattern: any credential NFT (diploma, passport, license, employee ID, etc.) proves possession only — zero on-chain fields; trust-anchor reuse and sub-type granularity are per-credential-type judgment calls, not a fixed rule.
- Passport: the first concrete credential — a pure travel-document NFT issued by 外務省, authority-only mint/burn, renewal modeled as burn-and-reissue. **No on-chain nationality credential exists** — 外務省 verifies nationality entirely off-chain, the same way a municipality verifies identity off-chain before minting `ResidentLink`. See [ADR 0006](decisions/0006-passport-credential.md).
- Diploma: the second concrete credential — issued from a school's existing corporate-registration address (no new trust mechanism); mint-once lifecycle (simplest so far); requires the recipient to hold a `ResidentLink` NFT at mint time (one-time, on-chain check) — no nationality distinction, since `ResidentLink` itself makes none. See [ADR 0007](decisions/0007-diploma-credential.md).
- License (driver's license): the third concrete credential — a single contract per prefecture (no per-vehicle-class split, unlike diploma — mirrors how one physical card already manages multiple classes today); suspension and revocation both represented identically on-chain as burn, with the real-world distinction kept off-chain; requires `ResidentLink` at mint, same pattern as diploma. See [ADR 0008](decisions/0008-license-credential.md).
- Health insurance: the fourth concrete credential — one contract per insurer; every insurer type (municipality, prefectural 広域連合, 協会けんぽ, 組合健保, 共済組合) maps onto an already-established trust mechanism, no new one needed; continuous (non-expiring) lifecycle unlike passport/license; requires `ResidentLink` at mint; no special handling for dependents. See [ADR 0009](decisions/0009-health-insurance-credential.md).
- Employee ID: the fifth concrete credential — issued from any registered corporation's existing corporate-registration address (no specific authority type); sole proprietors cannot issue it; one contract per company; continuous lifecycle like health insurance; **no `ResidentLink` precondition** — the first since passport, since employment isn't inherently tied to Japanese residency. See [ADR 0010](decisions/0010-employee-id-credential.md).
- Vaccination: the sixth and final originally-listed concrete credential — a municipality-issued, soulbound vaccination coupon with a genuine on-chain status field (`Issued`/`Vaccinated`), the second credential (after corporations) needing real mutable state. A hospital — not the municipality — flips the status, via a `VACCINATOR_ROLE` the municipality grants only to addresses already holding a valid corporate (医療法人) registration, checked on-chain; the hospital's actual legitimacy stays an off-chain determination. Multiple doses are multiple separate coupons; `Vaccinated` coupons are never burned. See [ADR 0011](decisions/0011-vaccination-credential.md).
- On-chain scope philosophy (2026-10-10): beyond identity/credentials/taxation/corporations, the project's scope now explicitly includes ~20 additional candidate systems across 8 new categories (political transparency, social welfare, public-interest finance, property/vital records, corporate/market transparency, judicial infrastructure, commerce/markets, plus Governance Core beyond voting) — all tracked 🔴 Not started in `docs/FEATURES.md`. Everyday commerce is in-scope for on-chain payment (same tax-transparency rationale as salary/income). Wealth-focused financial services are explicitly **not** pushed onto the same transparent rail — the service provider bears tax-compliance responsibility instead. High-frequency trading and personal wealth-accumulation investment are **deliberately excluded** (`🚫`), not silently omitted. See [ADR 0012](decisions/0012-onchain-scope-philosophy.md).
- A condensed copy of `docs/FEATURES.md` is now embedded directly in the root `README.md` for visibility (not just linked) — keep both in sync when a status changes.
- Standing guidance: current-law feasibility (e.g., "does a municipality have legal authority to do X") is not raised as a discussion point in this project — it's an explicit thought experiment, not aimed at real-world legal adoption.
- Voting: fully specified (2026-10-10, [ADR 0013](decisions/0013-voting-model.md)). Vote content is protected by a Helios-style scheme (homomorphic encryption + zero-knowledge proof of correct tally + threshold decryption across multiple trustees — no individual ballot is ever decrypted); vote participation uses the resident's existing `ResidentLink` address rather than a fresh per-election address, to avoid creating a new off-chain identity↔disposable-address mapping at the municipality. One generic election primitive (closed option list + one-hot encrypted ballots + homomorphic summation + pluggable seat-allocation method) covers referendums, single-seat plurality, multi-seat SNTV, and party-list proportional representation; ranked-choice/STV and write-in candidates are explicitly excluded. See [discussion log](state-design/voting/discussion-log.md) and [spec](state-design/voting/README.md).
- Legislative process: scoped out (2026-10-13, [ADR 0014](decisions/0014-legislative-process-scope.md)). Its core is already public and scrutinized, and its problems are institutional, so it is 🚫 Deliberately excluded. Two pieces are carved out: **direct-demand petition signatures** (own 🔴 item; residents sign from their `ResidentLink` address, making forgery like the 2020 Aichi recall case structurally impossible) and **legislators' roll-call vote records** (folded into political donations). The ADR also adopts a reusable **on-chain value test** for screening remaining candidates sub-part by sub-part. See [discussion log](state-design/legislative/discussion-log.md) and [spec](state-design/legislative/README.md).
- Political donations: fully specified (2026-10-13, [ADR 0015](decisions/0015-political-donations-model.md)). Each political organization's only lawful receiving address is a dedicated `PoliticalFund` contract; only genuine `ResidentLink` holders or registered corporations can contribute, verified against a new 総務省-operated `OfficialContractRegistry` (closing the deferred on-chain registry backlog item), so every donor is traceable without names on-chain. Per-recipient caps and "corporations → parties only" are enforced in-contract; cross-recipient totals and foreign donors are left to after-the-fact audit. Legislators' roll-call records are kept off-chain, partially superseding ADR 0014. See [discussion log](state-design/political-donations/discussion-log.md) and [spec](state-design/political-donations/README.md).
- Direct-demand petition signatures: fully specified (2026-10-17, [ADR 0016](decisions/0016-direct-demand-petition-model.md)). One `Petition` contract per demand, covering all six demand types, deployed by the election board with an explicit per-petition eligible list (each address must hold a registry-allowlisted `ResidentLink`), a full-text hash, and a fixed threshold. Residents sign from their own `ResidentLink` address; signatures are public, there are no collectors and no withdrawal. The board can only edit the list and pause/resume (paused time extends the end), all visible on-chain. The contract only certifies the count; the formal demand, any vote, objections, and relief stay off-chain. See [discussion log](state-design/direct-demand/discussion-log.md) and [spec](state-design/direct-demand/README.md).
- Executive: minimal v1 (2026-10-17, [ADR 0017](decisions/0017-executive-document-anchoring-v1.md)). Every agency registers the title and hash of each approval document in its own append-only `DocumentRegistry`; sensitive titles use a rule-based abbreviation. Detects rewriting after the fact; non-creation is knowingly not addressed. Validity condition, statistics, information disclosure and an authority registry are deferred to the redesign phase. See [discussion log](state-design/executive/discussion-log.md) and [spec](state-design/executive/README.md).
- Judiciary: fully specified (2026-10-17, [ADR 0018](decisions/0018-judiciary-model.md)). The core stays off-chain. Police and prosecutors register seized evidence at seizure in an append-only `EvidenceRegistry` (opaque case references; mapping disclosed to court and defence at indictment). Courts register records with retention classes in `CaseRecordRegistry`; disposal must be registered and is blocked for special-preservation records unless the class is first lowered publicly. Judgments are registered there, absorbing the "public court records" item. Enforcement: court-ordered disclosure of the debtor's `ResidentLink` address, on-chain tracing, seizure off-chain (no court role in the stablecoin). Token-juror arbitration 🚫; state-run purchase escrow moved to everyday commerce. See [discussion log](state-design/judiciary/discussion-log.md) and [spec](state-design/judiciary/README.md).
- Treasury / public finance: fully specified (2026-10-18, [ADR 0019](decisions/0019-treasury-model.md)). One `PublicTreasury` per public body; payments are stablecoin transfers tagged with a budget code (not capped), only to identified payees (`ResidentLink`, corporation, or another treasury via `OfficialContractRegistry`). Money is traceable past the first recipient with no extra mechanism. Payments to individuals, including public servants' pay and legislators' activity expenses, are public. Secret spending only through a public `OffChainExit`. **Project-wide principle adopted: whatever can be done off-chain is not put on-chain**, and whatever is off-chain is checked thoroughly off-chain. See [discussion log](state-design/treasury/discussion-log.md) and [spec](state-design/treasury/README.md).
- **Certified-address JPY stablecoin (project-wide premise)** (2026-10-18, [ADR 0020](decisions/0020-certified-address-stablecoin.md)): licensed JPY stablecoins move only between certified addresses (`ResidentLink`, corporations, registered public contracts, visitor passes); otherwise the transfer reverts, nothing is confiscated. Receiving funds at or from an uncertified address is illegal. Decertified balances leave only to certified successors (light path with owner signature; heavy path with municipality + court multisig, waiting period, owner veto). Foreign stablecoins lacking the rule are banned for domestic payments. See [spec](state-design/certified-stablecoin/README.md).
- VIP asset disclosure (2026-10-18, [ADR 0021](decisions/0021-vip-asset-disclosure.md)): no new contract; published `ResidentLink` address plus off-chain declarations (including ordinary deposits and non-JPY tokens), with severe penalties for omission. See [discussion log](state-design/vip-asset-disclosure/discussion-log.md) and [spec](state-design/vip-asset-disclosure/README.md).
- Public procurement (2026-10-24, [ADR 0022](decisions/0022-procurement-model.md)): one `Tender` per procurement from the body's `TenderFactory` (negotiated contracts included); commit–reveal sealed bids with deposits; ceiling price committed and revealed at opening; all bids public; lowest-price award checked on-chain; contracts and change contracts appended; rigging detection by off-chain analysis. See [discussion log](state-design/procurement/discussion-log.md) and [spec](state-design/procurement/README.md).
- Subsidies (2026-10-24, [ADR 0023](decisions/0023-subsidies-model.md)): no new contract; anchored grant decision plus treasury payments; subsidised expenses paid on-chain to certified addresses and listed as transactions instead of receipts (cash not eligible); expense reports anchored; everything public; kickbacks and duplicates detected off-chain. See [discussion log](state-design/subsidies/discussion-log.md) and [spec](state-design/subsidies/README.md).
- Pension (2026-11-07, [ADR 0024](decisions/0024-pension-model.md)): no new contract; the contribution transfer from the insured person's own `ResidentLink` address to one of two pension treasuries is the record; months allocated oldest-unpaid-first by law; employees pay their whole premium (employer half added to pay); entitlement decisions anchored by hash only; one generic benefit budget code; registered deaths stop payments via the burn; GPIF excluded. See [discussion log](state-design/pension/discussion-log.md) and [spec](state-design/pension/README.md).
- Benefits (2026-11-07, [ADR 0025](decisions/0025-benefits-model.md)): no new contract; treasury payments to the recipient's own address plus decisions anchored by hash; one budget code shared by all social-security payments to individuals (widening ADR 0024's); income checks only for applicants and recipients, with consent; medical and care assistance moved to the backlog. See [discussion log](state-design/benefits/discussion-log.md) and [spec](state-design/benefits/README.md).
- Unemployment insurance (2026-11-07, [ADR 0026](decisions/0026-unemployment-insurance-model.md)): no new contract; pension, benefits and subsidies patterns combined; the employee pays the insurance part, the employer alone the 二事業 part, into one treasury; working while receiving flagged from salary inflows or a new `EmployeeID`, with consent; training fees paid on-chain; workers' accident compensation and chain-computed statistics moved to the backlog. See [discussion log](state-design/unemployment-insurance/discussion-log.md) and [spec](state-design/unemployment-insurance/README.md).
- Personal data held by companies (2026-11-07, [ADR 0028](decisions/0028-personal-data-model.md)): a "don't hold it" law; personal data never on-chain; facts proved by credentials the person holds (new municipal age-threshold credentials); companies keep only address, fact and block; signature login; delivery addresses only to the carrier; daily access-log roots in a shared, event-only `AnchorRegistry`, a missing day being a violation. See [discussion log](state-design/personal-data/discussion-log.md) and [spec](state-design/personal-data/README.md).
- Real estate registry (2026-11-14, [ADR 0029](decisions/0029-real-estate-registry-model.md)): one `RealEstateToken` run by the Legal Affairs Bureau; moving the token is the transfer of the right; dealings off-chain, token transfer last; owner plus one agent to transfer; no lot number on-chain except for corporations, public bodies and VIPs; inheritance through the heavy successor path; mortgages as liens; no ownership by foreign corporations or non-Japanese non-residents (new kind `NonResidentOwner` for Japanese abroad); no migration from today's registry. See [discussion log](state-design/real-estate/discussion-log.md) and [spec](state-design/real-estate/README.md). Agents are per token and public (Round 5).

- 決定の経緯は [`docs/decisions/`](decisions/) のADRで、コードレベルの変更履歴は [`CHANGELOG.md`](../CHANGELOG.md) で管理。
- 国民・住民: 市区町村が発行する、譲渡不可(Soulbound)かつ国籍を問わない「住民登録リンク」NFT(住民であることの証明のみを行い、国籍は主張しない)。詳細は [ADR 0003](decisions/0003-resident-link-identity-model.md) を参照。
- 納税(個人の直接支払いのみ): 専用コントラクトなし — 住民の`ResidentLink`アドレスから、公式に証明された受取アドレスへの単純なステーブルコイン送金。詳細は [ADR 0004](decisions/0004-taxation-payment-rail.md) を参照。
- 法人: 登録・監督関係ごとに発行主体が発行する、譲渡不可・オンチェーンの登録NFT(法人は複数保有可)。役員・代表者の氏名はオンチェーンで公開、アドレスは一切非公開。法人自身のアドレスは、役員本人の個人鍵で署名するマルチシグが統治するコントラクト。詳細は [ADR 0005](decisions/0005-corporate-registration-model.md) を参照。
- 公的証明(一般パターン): どの証明NFT(卒業証明、パスポート、免許証、社員証等)も、保持の事実のみを証明する — オンチェーンのフィールドは一切なし。信頼の起点の流用、細分化の粒度は、固定ルールではなく証明の種類ごとの判断とする。
- パスポート: 最初の具体的な証明。外務省が発行する純粋な渡航文書NFTで、発行主体のみがmint/burnでき、更新はburn+再発行でモデル化する。**オンチェーンの国籍クレデンシャルは存在しない** — 外務省は、市区町村が`ResidentLink`発行前に本人確認を行うのと同じく、完全にオフチェーンで国籍を確認する。詳細は [ADR 0006](decisions/0006-passport-credential.md) を参照。
- 卒業証明: 2つ目の具体的な証明。学校の既存の法人登録アドレスから発行する(新しい信頼の仕組みは不要)。mintは一度きりという、これまでで最もシンプルなライフサイクル。受領者がmint時点で`ResidentLink`NFTを保有していることを要件とする(一度きりのオンチェーンチェック) — `ResidentLink`自体が国籍を区別しないため、国籍による区別はない。詳細は [ADR 0007](decisions/0007-diploma-credential.md) を参照。
- 免許証(運転免許証): 3つ目の具体的な証明。都道府県ごとに1つのコントラクト(卒業証明と異なり車両区分での分割はしない — 今日でも1枚の物理的な免許証で複数の区分を管理しているのを反映)。停止と取消はオンチェーンでは同一(burn)として扱い、現実の区別はオフチェーンに残す。mintには卒業証明と同じパターンで`ResidentLink`を要件とする。詳細は [ADR 0008](decisions/0008-license-credential.md) を参照。
- 健康保険証: 4つ目の具体的な証明。保険者ごとに1コントラクト。全ての保険者の種類(市区町村、都道府県の広域連合、協会けんぽ、組合健保、共済組合)が既存の信頼の仕組みに対応し、新しい仕組みは不要。パスポート・免許証と異なり、継続的な(期限切れのない)ライフサイクル。mintには`ResidentLink`を要件とする。扶養家族への特別な対応はなし。詳細は [ADR 0009](decisions/0009-health-insurance-credential.md) を参照。
- 社員証: 5つ目の具体的な証明。登録された法人であれば誰でも、既存の法人登録アドレスから発行できる(特定の機関の種類は問わない)。個人事業主は発行できない。会社ごとに1コントラクト。健康保険証と同じ継続的なライフサイクル。**`ResidentLink`の前提条件なし** — パスポート以来初めて、雇用は日本の住民資格と本質的に結びついていないため。詳細は [ADR 0010](decisions/0010-employee-id-credential.md) を参照。
- 接種証明: 当初挙げられていた6つ目で最後の具体的な証明。市区町村が発行する、譲渡不可の接種券で、実質的なオンチェーンの状態フィールド(`Issued`/`Vaccinated`)を持つ、法人に続き2例目のクレデンシャル。発行主体の市区町村ではなく**病院**がステータスを変更する。市区町村は、既に有効な法人登録(医療法人)を保有しているアドレスにのみ`VACCINATOR_ROLE`を付与する(オンチェーンで確認)。病院の実際の正当性はオフチェーンの判断のまま。複数回接種は複数の別々の接種券とし、`Vaccinated`になった接種券は決してburnしない。詳細は [ADR 0011](decisions/0011-vaccination-credential.md) を参照。
- オンチェーン化のスコープ方針(2026-10-10): 国民・住民/公的証明/納税/法人に加え、政治の透明性、社会保障、公益金融、財産・身分登記、法人・市場の透明性、司法インフラ、商取引・市場、統治の中核(投票以外)という8つの新しいカテゴリにまたがる、約20の追加候補システムを明示的にスコープに含めた — いずれも`docs/FEATURES.md`に🔴未着手として記録済み。日常の商取引はオンチェーン決済の対象(給与・所得と同じ納税の透明性という理由)。富裕層向け金融サービスは同じ透明な基盤には乗せず、提供者が納税処理の責任を持つ。高頻度取引と個人の資産形成目的の投資は**意図的に対象外**(`🚫`)とし、単に省略するのではなく明記する。詳細は[ADR 0012](decisions/0012-onchain-scope-philosophy.md)を参照。
- `docs/FEATURES.md`の凝縮版をルートの`README.md`に直接埋め込んだ(リンクだけでなく) — ステータスが変わったら両方を更新する。
- 恒常的な方針: 「市区町村にそれを行う法的権限があるか」のような現行法上の実現可能性は、このプロジェクトでは議論の対象としない — これは実社会への法制度化を目指すものではない、明示的な思考実験であるため。
- 投票: 設計確定(2026-10-10、[ADR 0013](decisions/0013-voting-model.md))。投票内容はHeliosスタイルの仕組み(準同型暗号+正しい集計のゼロ知識証明+複数の信頼主体に分散した閾値復号、個々の投票は誰によっても復号されない)で保護。投票参加は、選挙ごとの使い捨てアドレスではなく、住民が既に持つ`ResidentLink`アドレスを使用し、市区町村に新しい「身元↔使い捨てアドレス」のオフチェーン紐付けを作らないようにする。固定の選択肢集合+ワンホット暗号化された投票+準同型合計+差し替え可能な議席配分ルールという1つの汎用的な原理で、住民投票、単記投票による単一議席選挙、単記非移譲式の複数議席選挙、比例代表をカバーする。移譲式投票(STV)と自書式候補者は明示的に対象外。詳細は[議論ログ](state-design/voting/discussion-log.md)と[設計書](state-design/voting/README.md)を参照。
- 立法プロセス: スコープ外と決定(2026-10-13、[ADR 0014](decisions/0014-legislative-process-scope.md))。本体はすでに公開・監視されており、問題は制度面にあるため 🚫 意図的に対象外 とした。2つの部分を切り出す。**直接請求の署名**(独立した🔴項目。住民が自分の`ResidentLink`アドレスから署名し、2020年の愛知県知事リコールのような偽造を構造的に不可能にする)と、**議員の記名採決記録**(政治献金に含める)。あわせて、残りの候補を部分ごとにふるいにかける再利用可能な**オンチェーン価値テスト**を採用した。詳細は[議論ログ](state-design/legislative/discussion-log.md)と[仕様](state-design/legislative/README.md)を参照。
- 政治献金: 設計確定(2026-10-13、[ADR 0015](decisions/0015-political-donations-model.md))。各政治団体の唯一の適法な受け取りアドレスは専用の`PoliticalFund`コントラクトとする。献金できるのは本物の`ResidentLink`保有者か登記済み法人だけで、総務省が運用する新しい`OfficialContractRegistry`で確認する(先送りしていたオンチェーンレジストリのBACKLOG項目を解消)。これにより、オンチェーンに氏名を載せずにすべての献金者を追跡できる。受取先ごとの上限と「法人は政党のみ」はコントラクト内で強制し、受取先をまたぐ合計と外国人献金は事後監査に任せる。議員の記名採決記録はオフチェーンとし、ADR 0014を部分的に上書きした。詳細は[議論ログ](state-design/political-donations/discussion-log.md)と[仕様](state-design/political-donations/README.md)を参照。
- 直接請求の署名: 設計確定(2026-10-17、[ADR 0016](decisions/0016-direct-demand-petition-model.md))。請求ごとに1つの`Petition`コントラクトで6種類の請求をすべて扱う。選管が、請求ごとの有資格一覧(各アドレスはレジストリの許可リストにある`ResidentLink`を持つ必要がある)、全文ハッシュ、固定の必要数を持たせてデプロイする。住民は自分の`ResidentLink`アドレスから署名する。署名は公開され、受任者も撤回もない。選管にできるのは一覧の編集と一時停止・再開だけで(一時停止した時間は終了に加算)、すべてオンチェーンで見える。コントラクトは署名数の証明だけを行い、本請求、その後の投票、異議申し立て、救済はオフチェーンで扱う。詳細は[議論ログ](state-design/direct-demand/discussion-log.md)と[仕様](state-design/direct-demand/README.md)を参照。
- 行政: 最小の第1版(2026-10-17、[ADR 0017](decisions/0017-executive-document-anchoring-v1.md))。すべての行政機関は、各決裁文書の名称とハッシュを自らの追記専用の`DocumentRegistry`に登録する。機微な名称はルールに基づく略称を使う。事後の書き換えは検出できるが、記録を作らないことは承知のうえで扱わない。効力の条件、統計、情報公開、権限レジストリは再設計の段階に先送りする。詳細は[議論ログ](state-design/executive/discussion-log.md)と[仕様](state-design/executive/README.md)を参照。
- 司法: 設計確定(2026-10-17、[ADR 0018](decisions/0018-judiciary-model.md))。本体はオフチェーンのまま。警察と検察は押収した証拠を押収の時点で追記専用の`EvidenceRegistry`に登録する(秘匿化した事件参照。対応関係は起訴時に裁判所と弁護側に開示)。裁判所は記録を保存区分とともに`CaseRecordRegistry`に登録する。廃棄は登録が必要で、特別保存の記録は公開で区分を下げない限り廃棄できない。判決もここに登録し、「判決等の公開」の項目を吸収する。執行: 裁判所の命令による債務者の`ResidentLink`アドレスの開示、オンチェーンでの追跡、オフチェーンでの差押え(ステーブルコインに裁判所の権限は持たせない)。トークン陪審員による仲裁は🚫、国が運営する購入時のエスクローは日常の商取引へ。詳細は[議論ログ](state-design/judiciary/discussion-log.md)と[仕様](state-design/judiciary/README.md)を参照。
- 歳出・予算: 設計確定(2026-10-18、[ADR 0019](decisions/0019-treasury-model.md))。公的機関ごとに1つの`PublicTreasury`。支払いは予算コード(上限ではない)を付けたステーブルコインの送金で、身元の分かる支払先(`ResidentLink`、法人、`OfficialContractRegistry`で確認する別の国庫)にだけ支払う。特別な仕組みなしに最初の受取人より先まで追える。公務員の給与や議員の政務活動費を含め、個人への支払いは公開する。秘密の支出は公開の`OffChainExit`を通す場合に限る。**プロジェクト全体の方針を採用: オフチェーンでできることはオンチェーン化せず**、オフチェーンの部分はオフチェーンで徹底してチェックする。詳細は[議論ログ](state-design/treasury/discussion-log.md)と[仕様](state-design/treasury/README.md)を参照。
- **認定アドレス制の円建てステーブルコイン(プロジェクト全体の前提)**(2026-10-18、[ADR 0020](decisions/0020-certified-address-stablecoin.md)): 認可された円建てステーブルコインは、認定アドレス(`ResidentLink`、法人、登録された公的なコントラクト、旅行者パス)の間でしか動かない。それ以外の送金はリバートし、没収はしない。認定外のアドレスで、またはそこから資金を受け取ることは違法。認定を失った残高は、認定済みの承継先にしか出ていけない(持ち主の署名がある軽い手続き、役所と裁判所のマルチシグ・待機期間・持ち主の拒否権を伴う重い手続き)。このルールを持たない外国のステーブルコインの国内での決済利用は禁止。[仕様](state-design/certified-stablecoin/README.md)を参照。
- 要人の資産公開(2026-10-18、[ADR 0021](decisions/0021-vip-asset-disclosure.md)): 新しいコントラクトは作らない。公表された`ResidentLink`アドレスと、オフチェーンの申告(普通預金と円以外のトークンを含む)。申告漏れには厳罰。[議論ログ](state-design/vip-asset-disclosure/discussion-log.md)と[仕様](state-design/vip-asset-disclosure/README.md)を参照。
- 公共調達(2026-10-24、[ADR 0022](decisions/0022-procurement-model.md)): 調達ごとに、機関の`TenderFactory`から1つの`Tender`(随意契約を含む)。保証金付きのコミット・リビールによる封印入札。予定価格はコミットし開札時に明かす。すべての入札を公開。最低価格による落札はオンチェーンで確認。契約と変更契約を追記。談合の検出はオフチェーンの分析。[議論ログ](state-design/procurement/discussion-log.md)と[仕様](state-design/procurement/README.md)を参照。
- 補助金(2026-10-24、[ADR 0023](decisions/0023-subsidies-model.md)): 新しいコントラクトは作らない。アンカーした交付決定と国庫の支払い。補助対象の経費はオンチェーンで認定アドレスに支払い、領収書の代わりに取引として列挙する(現金は対象外)。実績報告をアンカー。すべて公開。キックバックと重複はオフチェーンで検出。[議論ログ](state-design/subsidies/discussion-log.md)と[仕様](state-design/subsidies/README.md)を参照。
- 年金(2026-11-07、[ADR 0024](decisions/0024-pension-model.md)): 新しいコントラクトは作らない。被保険者自身の`ResidentLink`アドレスから年金の2つの国庫のいずれかへの送金が記録になる。何月分に充てるかは法律で未納の最も古い月からと固定。会社員は保険料を全額自分で払う(雇用主負担分は給与に上乗せ)。年金額を変える決定はハッシュだけをアンカリング。給付の予算コードは1つ。届出済みの死亡はburnで支払いが止まる。GPIFは対象外。[議論ログ](state-design/pension/discussion-log.md)と[仕様](state-design/pension/README.md)を参照。
- 各種手当(2026-11-07、[ADR 0025](decisions/0025-benefits-model.md)): 新しいコントラクトは作らない。受給者本人のアドレスへの国庫の支払いと、ハッシュでアンカリングした決定。個人への社会保障の支払いすべてに共通の予算コードを1つ(ADR 0024を拡張)。収入確認は申請者と受給者に限り、同意に基づく。医療扶助・介護扶助はバックログへ。[議論ログ](state-design/benefits/discussion-log.md)と[仕様](state-design/benefits/README.md)を参照。
- 雇用保険(2026-11-07、[ADR 0026](decisions/0026-unemployment-insurance-model.md)): 新しいコントラクトは作らない。年金・各種手当・補助金の型を組み合わせる。労使負担の部分は従業員が、二事業の部分は雇用主だけが、1つの国庫に払う。受給中の就労は、同意に基づき給与の入金や新しい`EmployeeID`から検知。受講料はオンチェーンで支払う。労災保険とチェーンから計算する統計はバックログへ。[議論ログ](state-design/unemployment-insurance/discussion-log.md)と[仕様](state-design/unemployment-insurance/README.md)を参照。
- 企業が保有する個人情報(2026-11-07、[ADR 0028](decisions/0028-personal-data-model.md)): 「持たせない」法律。個人情報はオンチェーンに載せない。事実は本人が持つクレデンシャルで証明する(市区町村による年齢の基準のクレデンシャルを新設)。企業が保持するのはアドレス、事実、ブロックだけ。署名でログイン。配送先の住所は配送業者にだけ。アクセスログの毎日のルートを、イベントだけを出す共有の`AnchorRegistry`に記録し、欠落した日は違反。[議論ログ](state-design/personal-data/discussion-log.md)と[仕様](state-design/personal-data/README.md)を参照。
- 不動産登記(2026-11-14、[ADR 0029](decisions/0029-real-estate-registry-model.md)): 法務局が運用する`RealEstateToken`を1つ。トークンの移転が権利の移転。取引はオフチェーンで、トークンの移転が最後。移転には所有者と1人以上の代理人。地番はオンチェーンに載せず、法人・公的機関・要人の土地だけを公開。相続は重い承継の手続きで。抵当権は担保として記録。外国法人と日本国籍を持たない非居住者は所有できない(海外の日本人には新しい種類`NonResidentOwner`)。現在の登記からの移行はない。[議論ログ](state-design/real-estate/discussion-log.md)と[仕様](state-design/real-estate/README.md)を参照。代理人はトークンごと、公開(Round 5)。

## 未解決の論点

- メインネットでどのチェーンを採用するか(Ethereum mainnet vs. Polkadot Hub mainnet) — テスト段階でより多くの知見を得てから決定。
- 新たに拡大したロードマップ(`docs/FEATURES.md`参照)の中で、次にどのシステムを設計するか — 多くの🔴候補(政治献金、財務、年金、寄付/クラウドファンディング、不動産登記等)が出そろったが、互いの優先順位はまだ決めていない。政治献金は設計確定済み(2026-10-13)。残りの候補はオンチェーン価値テスト([ADR 0014](decisions/0014-legislative-process-scope.md))でふるいにかける。
- 「富裕層向け金融サービス: 提供者による納税処理」の具体的な設計(ADR 0012は方針のみを記録し、コントラクト設計は含まない) — そのカテゴリに着手する時点まで保留。
- 当初の6つ(パスポート、卒業証明、免許証、健康保険証、社員証、接種証明)を超える追加の公的証明が必要かどうか — 現時点では予定なし。ただしパターンは十分検証済みなので、今後出てきても対応可能。
- プロジェクト自体のガバナンスモデル(コントラクトの「憲法」部分の変更を誰が提案・承認できるか)。
- フロントエンド以外のオフチェーンコンポーネント(インデクシング、通知等)が必要かどうか — 現時点では不要。具体的な機能要件が出てから検討(YAGNI)。
